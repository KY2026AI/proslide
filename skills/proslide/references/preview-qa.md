# ProSlide Preview QA

HTML 预览生成后读取本文件。先做四层防打回质检，再把预览交给用户确认。质检目标不是让页面炫，而是让这份材料能被目标受众快速理解、减少返工。

## 四层防打回质检

### L1 页面硬伤检查

像代码语法检查一样，逐页排除硬错误：

- 页面是否为 `1280×720` 的 `.slide`
- 标题是否完整位于顶部横线以上
- 顶部横线是否完整，并与内容区左右对齐
- logo 是否存在、加载成功、没有拉伸变形
- logo 是否完整位于顶部横线上方，底部没有覆盖或贴住横线；建议 logo 底部与横线顶部保留约 10px 间距，同时不要过度贴近页面顶部
- 是否有核心观点条/结论条
- 是否存在纯大段文字堆叠
- 是否存在文字溢出、裁切、重叠或被图片遮挡
- 是否存在“未出画布但内部覆盖”的版式问题：例如后续模块覆盖前一模块、下方结论块压住矩阵/流程/图表、容器高度被压缩导致内容只显示上半部分
- 图片是否完整显示，是否存在破图
- 浏览器实际计算字号是否满足下限；任一业务正文低于下限即不通过
- 卡片、列、时间线、图表是否网格对齐
- 内容较少的卡片型组件是否垂直居中，且不限于 `.card`
- 低信息量卡片是否被 `flex: 1`、大 `min-height`、等高网格或固定高度强行撑满页面；若每张卡只有标题 + 1-3 行正文 / 1-3 个 bullet，却占据大面积高度，判定为 L1 硬伤
- 对主要卡片型组件做内容密度检查：内容实际高度低于容器高度约 50% 时必须重排或缩短容器；低于约 40% 时不得交付用户确认
- 是否有低对比度文字或过浅图标
- 是否存在用中文、英文字母、数字、emoji 伪装成图标的情况；如果有，必须替换为语义 SVG 图标或真实图片
- 是否有过多留白或内容过度拥挤
- 明显留白是否已用语义视觉或版式重排处理
- 是否出现“文字偏小但仍有大块连续空白”；若出现，判定为空间分配失败
- 大块留白是否由空卡片、空流程节点、空矩阵格造成；若是，必须改成紧凑条形、信息图、判断信号、适用条件或案例启发

任何 L1 问题都必须先修复，禁止交给用户确认。

### L2 版式逻辑检查

检查“内容关系”和“页面结构”是否匹配：

- 并列关系是否使用网格/同构卡片
- 对比关系是否使用左右对照或差异表述
- 流程关系是否使用时间线/步骤流
- 数据指标是否突出主指标和支撑数据
- 问题-方案是否能看出问题、原因、动作的对应关系
- 页面主版式是否由内容关系触发，而不是为了复刻某个模板外观；若只是换了颜色、形状或装饰，但信息结构仍是罗列，必须重排
- 卡片是否只用于真正的同级并列信息；若页面明明是流程、对比、因果、层级、数据或案例，却被强行拆成卡片，必须换成对应版式
- 明确框架词是否触发专属布局：SWOT、PDCA、PEST、5W2H、RACI、OKR 等不能退化成普通卡片页
- 时间计划类内容是否呈现节奏、里程碑、状态或责任；若只是事项列表，必须改成时间线、甘特、泳道或周计划矩阵
- 图表页是否形成“观点 + 主图 + 旁注 + 口径 + 业务动作”的证据链；若图表孤立存在，必须补齐解释关系或调整版式
- 案例页是否呈现“问题 -> 做法 -> 效果 -> 启发”的链路；若只是案例名称堆叠，必须重组
- 整稿是否过度依赖卡片式网格；连续 3 页以上都是卡片阵列，或多数页面第一眼都是圆角块堆叠时，判定为模板感偏强，必须重排部分页面
- 核心结论是否先出现，而不是让用户从细节里猜结论
- 同级信息是否同构呈现
- 同级图标是否风格统一、语义匹配；图标是否帮助目标受众先看出主要关系，例如流程顺序、对象类别、动作结果或层级结构
- 是否出现模板化布局；若版式只是机械三卡片、等宽空卡或泛化图标堆叠，必须按内容关系重排。
- 流程卡、并列卡、矩阵卡的容器尺寸是否由内容密度驱动；低信息量内容应使用紧凑流程条、横向条目、信号组或词典式卡片，而不是撑满页面
- 页面留白是否承担语义功能；如果留白只是被空容器占掉，必须补足“判断条件 / 适用边界 / 输入-规则-输出 / 迁移启发”等内容，或直接缩短模块
- 主版式是否被次要模块挤压。若一页的主形态是矩阵、时间线、流程图、漏斗或数据图表，底部结论块/补充说明不得压缩或覆盖主图；必要时删除重复结论块，把结论融入核心观点条或主图标签
- 阅读顺序是否自然，视线是否能从结论到证据再到动作

如果 L2 不通过，优先重组页面结构，而不是微调颜色或字号。

### L3 汇报内容检查

检查这页是否具备汇报所需的内容支撑：

- 结论是否有数据、事实、案例或对比支撑
- 问题是否有归因，避免只描述现象
- 方案是否有优先级，避免动作平铺
- 下一步是否有节奏、责任、指标或判断标准
- 内容是否回应受众关切
- 是否存在“只讲成果不讲风险”“只讲动作不讲原因”“只讲结论不讲证据”
- 是否有明显逻辑跳跃，需要补充背景或过渡
- 是否保持正式汇报语气：表达应克制、准确、清晰，适合会议室呈现；不得过度口语化、聊天化或网络化。
- 是否有浓重“AI味”：空泛形容词、万能口号、抽象堆叠、没有对象和动作的标题，例如“全面赋能、闭环协同、价值跃迁、智能化升级新范式”等。发现后必须改成正式、具体的对象、动作和变化。
- 是否堆叠行业黑话或圈内术语。非目标受众熟悉的术语必须减少、替换或补一句简洁的业务解释；一页内不应连续出现多个未解释术语。
- 标题、核心观点和卡片文案是否像正式汇报材料，而不是模板生成、宣传口号、概念拼接或聊天口吻。应改写为“问题是什么 / 做了什么 / 带来什么变化 / 对管理或业务意味着什么”。

如果素材不足，标记为“需用户补充”，不要编造事实。

### L4 会议室终审

用 10 秒会议室测试审视每页：

- 一个不了解背景的人看 10 秒，是否知道本页想表达什么
- 如果只看标题、核心观点条和关键数字，会不会误解
- 这页是否需要汇报人解释太多背景才能成立
- 这页是否因为黑话、AI式口号或抽象词过多，导致非本领域同事 10 秒内抓不住意思；若是，必须降术语密度并改成正式、易懂的汇报语言
- 讲完这一页，下一步动作是否自然
- 页面第一眼看到的是结论，还是装饰

若 L4 不通过，优先重写核心观点条，或把页面拆成“结论-证据-动作”的结构。

## HTML 自查清单

完成四层质检后，再做一遍基础 HTML 自查：

- 主内容是否与核心观点对齐
- 页面间风格是否统一
- 页码/标题/Logo 等固定元素是否一致
- 所有图片是否可访问
- 检查 CSS 是否存在可疑拉伸模式：低信息量模块使用 `flex: 1`、`height: 100%`、过大的 `min-height`、`align-content: stretch`、`justify-content: space-between` 等；发现后必须人工判断是否造成空卡
- 浏览器缩放或截图时是否保持清晰
- 同时检查原尺寸页面和缩略图；只有字号、空间分配和信息层级均清晰才算通过
- 除 DOM 边界检查外，必须查看关键页面截图。自动检查只能发现出界、破图和明显裁切，不能替代对主版式是否被压缩、覆盖或空框撑版式的人工视觉判断。

## 浏览器预览

优先使用浏览器打开 HTML 预览。若环境不允许直接打开 `file://`：

1. 启动本地只读 HTTP 服务。
2. 打开本地 URL。
3. 截图或描述预览状态。
4. 不要因此跳过用户确认。

## 固定交付话术

HTML 预览完成后，用类似格式回复：

```md
HTML 预览已生成：[文件路径]
我已做过四层防打回质检：页面硬伤、版式逻辑、汇报内容、会议室 10 秒可读性均已检查。

请确认：这版 HTML 预览是否需要调整？
同时请确认是否需要生成讲稿：需要 / 不需要。
```

## 用户反馈处理

- “留白多/字太小”：先精简文案和重组层级，再更换版式或拆页；禁止用小字体和固定等高容器强塞内容。
- “卡片内容贴顶部 / 大空卡”：检查所有卡片型组件，而不只是 `.card`；低信息量卡片不得撑满大容器。先缩短容器或改成紧凑条形/流程/信号组，再考虑垂直居中；必要时补充有语义的判断条件、适用边界或案例启发。
- “图标像文字标号”：立即替换为语义 SVG 图标；中文、数字、字母只能作为标签或编号，不能作为图标本体。
- “太挤”：先压缩文案和合并层级，再收窄 padding/gap，最后才降低字号。
- “文字罗列”：改成卡片、时间线、流程图、对比栏或数据卡片。
- “AI味/模板感强”：先检查版式是否由内容关系驱动；机械三卡片、等宽空卡、泛化图标堆叠需重排。不要通过搜集或复刻更多截图模板解决，应回到并列、对比、递进、分解、时间计划、分析框架、数据证据等关系判断。
- “AI味/黑话太重”：先删掉空泛形容词和万能口号，再把术语换成正式汇报语言中的业务对象、具体动作和可理解结果；必要术语保留但必须补一句简洁解释。注意不要改成聊天式口语。
- “重点不突出”：增加核心观点条、主指标、状态标签、颜色对比。
- “图片不好看/看不清”：优先完整显示原图，必要时放大图片区或拆到单独页。
- “表达不准确”：只改用户指出的含义，不擅自编造事实。
- “逻辑还是不清楚”：回到 L3 汇报内容检查，补齐结论、证据、归因、动作的关系。
- “目标受众可能还是看不懂”：回到 L4 会议室终审，重写核心观点条并减少解释成本。

修改后必须重新生成 HTML 预览，并再次等待用户确认。
